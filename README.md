# RideConnect MVP

A mobile-friendly front-end demo for RideConnect, a ride-hailing concept starting in Mbala, Northern Province, Zambia. It uses plain HTML, CSS and JavaScript and runs without a build step or package installation.

## Run locally

1. Check out `copilot/rideconnect-mvp` (or your development branch).
2. Open `index.html` in a modern browser, or serve this folder:

   ```bash
   python3 -m http.server 8000
   ```

3. Visit `http://localhost:8000`.

No dependency install, API key, or environment variables are required. Google Fonts are optional; system sans-serif fonts are used if the font service is unavailable.

## Demo features

- Responsive RideConnect landing page and navigation with passenger and driver registration/login tabs.
- Zambian mobile validation for 9 digits starting with 7 or 9, optionally with `+260`, `260`, or a leading `0`; spaces, hyphens, and parentheses are allowed for formatting.
- Passenger booking with route inputs, passenger count, phone validation, a clearly labelled illustrative Kwacha estimate, pending-request cancellation, status filtering, and success/error feedback.
- Driver dashboard with clearly labelled sample scenarios and passenger-created demo requests, status filtering, availability toggle, accept/reject confirmation prompts, and result feedback.
- Admin overview of browser-local passenger and driver profiles, availability controls, aggregate statistics, and searchable/filterable passenger-created requests.
- Contextual empty states guide each dashboard when there is no data or no match. Mobile navigation closes on selection and Escape.
- Profiles and ride data persist in the existing browser `localStorage` key (`rideconnect-mvp-v1`). The existing data structure remains in use; demo scenario decisions continue in the existing `demoStatuses` field. Clear site data to reset the demo.

## Important limitations

This is a user-interface MVP, not a deployed ride-hailing service. There is no backend, database, secure authentication or identity verification, password-based login, protected admin authorization, dispatch, payment integration, SMS/phone verification, route calculation, live GPS, or connected driver network. Login is a local demo lookup by phone number and is not account security. The admin view is not access-controlled. Data remains in one browser/device and should be fictional; do not enter real personal information.

Fare figures are generated by a simple deterministic demo formula and are not based on route distance, actual Mbala rates, a pricing provider, or a quote. Sample scenarios and their displayed figures are fictional UI data, not actual drivers, bookings, operating services, or market prices. Submitting or accepting a request does not contact a passenger or driver.

Before launch, add a server-side API and persistent database, proper authentication and authorization (including protected admin access), privacy/security practices, validated Mbala fare and route rules, operational driver onboarding, and any needed communications/payment providers. Keep service credentials on the server, never in browser code.

## Review and testing notes

The navigation, form listeners, request state transitions, filter controls, markup IDs used by the app, and browser persistence paths were reviewed. No package/build or automated browser test suite is configured. A JavaScript syntax check can be run with `node --check app.js` where Node.js is installed. Manual browser/device QA is still needed:

1. Navigate through header/footer links, use browser back/forward, and open the mobile menu; verify selection and Escape close it.
2. Register and log in with demo profiles. Test valid numbers such as `971234567`, `0971234567`, and `+260 97 123 4567`, plus invalid length/prefix/characters.
3. Create a passenger request, verify confirmation, request card and status filter; test missing/equal locations and invalid phone. Cancel and verify status.
4. As a registered driver, toggle availability, test accept while unavailable, then accept/reject with confirmation and verify result feedback and status filtering. Reload to verify local persistence.
5. Check empty/populated passenger, driver and admin states; test admin search/status filters and driver availability controls.
6. Inspect at narrow mobile widths and desktop; check menu, forms, cards, filters and dashboards for overflow and keyboard usability.
